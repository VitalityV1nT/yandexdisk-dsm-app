# Changelog — ARM-сборка

Все изменения ARM64-версии пакета. Базовый пакет — x86_64
`0.1.6.1080-3` (ветка `main`).

## Версионирование

С версии **1.0.0** ARM-сборка ведёт собственную линию версий по правилам
**семантического версионирования** `МАЖОР.МИНОР.ПАТЧ`:

- **МАЖОР** (первая цифра) — крупные/несовместимые изменения;
- **МИНОР** (вторая цифра) — новая функциональность с обратной совместимостью;
- **ПАТЧ** (третья цифра) — исправления ошибок.

Изменение любого разряда **обнуляет все разряды правее** (напр. `1.4.7` →
минор → `1.5.0`; → мажор → `2.0.0`). DSM-суффикс сборки (`-N`) больше не
используется: повторный выпуск без изменения исходников — это ПАТЧ.

Версию для каждой задачи **определяет ИИ, выполняющий задачу**, исходя из
характера изменений.

## [1.0.0] (ARM) — 2026-05-30

Первая стабильная версия ARM-сборки. Счётчик версий **сброшен до `1.0.0`**:
ARM-порт (движок rclone, aarch64, своя модель синхронизации) достаточно разошёлся
с базовым x86-пакетом, чтобы вести собственную линию версий, отвязанную от
`0.1.6.1080`.

### Changed
- **Введено семантическое версионирование** `МАЖОР.МИНОР.ПАТЧ` с обнулением
  младших разрядов и без DSM-суффикса сборки (`-N`); правила и порядок выбора
  версии — в разделе «Версионирование» выше. Версию определяет ИИ, выполняющий
  задачу.
- `spk/INFO`: `version` `0.1.6.1080-15` → `1.0.0`. Имя артефакта теперь
  `YandexDisk-ARM-1.0.0.spk`. Функционально пакет идентичен `0.1.6.1080-15` —
  меняется только строка версии. Апгрейд с прежней версии DSM распознаёт штатно
  (`1` > `0` в старшем разряде; пакет уже принимал 4-сегментные версии).

## [0.1.6.1080-15] (ARM) — 2026-05-30

Сборка и релиз-процесс: версия в имени артефакта и автоматизация GitHub.

### Changed
- **Имя `.spk` содержит версию.** `build.sh` подставляет версию из `spk/INFO` в имя
  файла — `YandexDisk-ARM-<версия>.spk` (напр. `YandexDisk-ARM-0.1.6.1080-15.spk`)
  вместо безымянного `YandexDisk-ARM.spk`. Ассеты GitHub Release теперь
  самоописательны, а ревизии не перезаписывают друг друга. Версия читается один раз
  в начале сборки (убрано дублирующее чтение `spk/INFO`).

### Added
- **CI/Release через GitHub Actions** (`.github/workflows/build-spk.yml`). На каждый
  push/PR (`main`/`arm-support`) — сборка `.spk` + статические проверки, результат
  доступен как workflow artifact. На тег `v*` — сборка и **публикация** версионного
  `.spk` + `.sha256` как ассетов GitHub Release (через `gh`, без сторонних actions;
  `permissions: contents: write`). Runner `ubuntu-latest` уже содержит
  `unzip`/`curl`/`shellcheck`/`python3`, поэтому `build.sh` отрабатывает «как есть»
  (докачивает rclone по контрольной сумме).
- **Документация по сборке в `README-ARM.md`** — раздел «🛠 Сборка пакета»:
  локальная сборка (`./build.sh`, зависимости, шаги, проверка SHA-256) и
  сборка/релиз через GitHub Actions (тег → Release). Зафиксирован `eol=lf` для
  `*.yml`/`*.yaml`.

## [0.1.6.1080-14] (ARM) — 2026-05-30

Набор «P1» из аудита: снижение фоновой нагрузки на DS124 (1 ГБ RAM),
диагностируемость синхронизации в UI и сокращение технического долга после
миграции с x86-демона на rclone.

### Removed
- **C2 — ежечасный `yandex-cleaner` удалён.** Постоянный фоновый процесс раз в час
  рекурсивно обходил всю папку синхронизации и делал `rm -rf @eaDir` + удалял
  `Thumbs.db`. Это было и бесполезно (`bisync` и так исключает `@eaDir/**` и
  `Thumbs.db` — наверх они не уходят), и вредно: удаление `@eaDir` воюет с
  медиа-индексатором Synology, который тут же пересоздаёт их (бесконечная
  churn-петля + потеря миниатюр). Опциональная локальная чистка теперь —
  **один шаг внутри `sync`** (`clean_thumbs=1` в `config.cfg`, по умолчанию выкл.),
  и удаляет только `Thumbs.db`/`.DS_Store`, **не трогая** `@eaDir`.
- **D2 — мёртвый код.** Удалён неиспользуемый эндпойнт `last_status.cgi` (UI ходит
  только в `status.cgi`/`log.cgi`/`sync_log.cgi`) и связанный с ним `last_status.log`.

### Added
- **E1 — лог синхронизации виден в UI.** Новая вкладка **«Синхронизация»**
  (`sync_log.cgi`) показывает последние 300 строк `var/logs/rclone.log` — при
  `rc=N`/конфликте причина видна прямо в интерфейсе, без SSH. Раньше реальный вывод
  bisync нигде в UI не отображался (только `error|время|rc=N` в истории статусов).
- **F1 — бинарники убраны из git.** `spk/package/rclone` (72 МБ) и
  `YandexDisk-ARM.spk` (24 МБ) больше не отслеживаются — раздаются как
  **GitHub Release assets**. `build.sh` воспроизводит `rclone` из официального
  релиза по контрольной сумме (сверка SHA256 и zip, и распакованного бинарника) и
  пересобирает `.spk`. Зип кэшируется локально в `downloads/` (тоже вне git).
  Сборка `.spk` сделана **воспроизводимой байт-в-байт** (фиксированные mtime +
  `gzip -n`), поэтому SHA-256 в `RELEASE-INFO-ARM.txt` повторяется при чистой
  пересборке, а не меняется от прогона к прогону.

### Changed
- **A4/A5/D2 — `yandex-logger` переписан под новую модель.** Был резидентный
  bash-цикл, который раз в 60 c звал `yandex-disk status` (а тот — `rclone`), вызывал
  обёртку по `PATH` (мог получить пустой статус из systemd-юнита) и содержал мёртвую
  ветку «Error: daemon not started» от x86-демона. Теперь это лёгкий **heartbeat на
  POSIX sh**: читает `var/sync.state` напрямую (без спавна `rclone`/обёртки), пишет
  историю по изменениям состояния, интервал 5 мин. Назначение прежнее — держать
  пакет «Запущено» на DSM 7 (по живому процессу `start-stop-status status`
  возвращает `0`); удешевлён, но не удалён.
- **C3 — ротация логов.** `rclone.log` (пишет `sync`) и `status_history.log` (пишет
  heartbeat) ротируются по размеру (>1 МБ → `.1`, одна резервная копия) — раньше
  росли без ограничения.
- **D1 — общий `common.sh`.** Пути пакета, парсер `config.cfg` (`cfg()`), ротация
  логов (`rotate_log`) и сводка `sync.state` (`sync_state_line`) вынесены в
  `target/common.sh` и подключаются (`.`) обёрткой, `start-stop-status` и логгером.
  Раньше путь `/var/packages/YandexDisk` и парсер `dir` дублировались по нескольким
  файлам (приходилось править в двух местах). Переменная `DAEMON_LOG` (наследие
  демона) переименована в осмысленную `RCLONE_LOG`.
- **D3/D4 — чистка скриптов.** `start-stop-status stop` теперь матчит
  `/scripts/yandex-logger`, а не подстроку `yandex-logger` в любой команде.
  Все скрипты пакета приведены к **POSIX sh** (bash-зависимость ушла вместе с
  `yandex-cleaner`); `build.sh` проверяет их единым `dash -n` + `shellcheck`
  (линт чистый).

## [0.1.6.1080-13] (ARM) — 2026-05-30

Набор «P0» из аудита: корректность синхронизации, диагностируемость и снижение
накладных расходов на целевом железе (DS124, 1 ГБ RAM).

### Fixed
- **A1 — конфликт-резолюция приведена в соответствие с README.** `rclone bisync`
  запускается с `--conflict-resolve path1`: при двустороннем изменении одного файла
  побеждает **локальная** копия (как и обещала документация). Выбор `path1`, а не
  `newer`, намеренный — бэкенд Yandex не хранит mtime точно (см. `-11`), поэтому
  решение «по новизне» было бы недетерминированным. Конфликтная версия с Диска не
  теряется: сохраняется рядом как переименованная копия. Раньше bisync шёл без
  `--conflict-resolve` (дефолт `none`) и плодил дубликаты `..path1/..path2`.
- **A3 — лог реальной синхронизации сохраняется.** `_bisync` получил
  `--log-file var/logs/rclone.log --log-format date,time`. Раньше переменная
  `DAEMON_LOG` была объявлена, но не использовалась, и причина сбоя bisync не была
  видна ни в UI, ни в файле (только `rc=N`). Само-восстановление базы (`--resync`)
  теперь распознаёт триггер «cannot find prior / Must run --resync» и в лог-файле,
  и в перехваченном stderr.

### Added
- **A2 — защита от перекрытия запусков (`flock`).** `yandex-disk sync` берёт
  неблокирующий `flock` на `var/sync.lock`: если предыдущий прогон (например,
  долгий первичный `--resync`) ещё идёт, повторный запуск из Планировщика тихо
  завершается («sync already running, skip») и не конкурирует за кэш bisync.

### Changed
- **C1 — версия rclone кэшируется.** `status` больше не спавнит 72 МБ-бинарник
  rclone на каждый вызов (логгер опрашивал статус раз в минуту → ~1440 запусков
  в сутки только ради неизменной строки версии). Версия читается из
  `var/rclone.version`; `start-stop-status` сбрасывает кэш при (пере)старте пакета,
  чтобы подхватить обновление rclone.
- **G1 — `README-ARM.md` вычищен от наследия резидентного демона.** Убраны
  противоречивые упоминания «резидентного демона» (установка, Шаг 5, раздел
  расписания) и неиспользуемый параметр `interval` из примера `config.cfg`. Единая
  модель — «Планировщик задач DSM». Добавлено указание на лог `var/logs/rclone.log`.

## [0.1.6.1080-12] (ARM) — 2026-05-29

### Changed
- **Убран резидентный sync-демон.** На DSM 7 фоновый shell-цикл ненадёжен под
  systemd (его прибивает, остаются bisync-блокировки, пакет уходит в «остановлен»).
  Теперь периодическая синхронизация настраивается как задача **Планировщика задач
  DSM**, запускающая `yandex-disk sync`.
  - `start-stop-status` больше не запускает bisync-цикл; стартует только лёгкие
    `yandex-logger`/`yandex-cleaner` (статус в UI + пакет показывается «запущен»),
    статус определяется по `yandex-logger`.
  - Обёртка `yandex-disk`: убраны `start/stop/__daemon`; остались
    `sync | status | setup | version | rclone`. `sync` сам пишет `sync.state`
    (его читает `status`/UI), несёт `--inplace`, `--max-lock`, `--recover`,
    `--check-sync=false` и авто-`--resync` при потере базы.
  - `interval=` в `config.cfg` больше не используется (период задаётся в Планировщике).

## [0.1.6.1080-11] (ARM) — 2026-05-29

### Fixed
- **`--check-sync=false`**: бэкенд Yandex в rclone не сохраняет mtime точно, из-за чего
  строгая взаимная сверка bisync падала с «path1 and path2 are out of sync / Modtime not
  equal in listing» даже для идентичных по содержимому файлов (напр. local `2014` vs
  remote `2026`). Теперь расхождение mtime во взаимной сверке допускается.

## [0.1.6.1080-10] (ARM) — 2026-05-29

### Fixed / Changed
- **`--inplace`**: rclone пишет сразу в целевой файл, без временного `.partial`.
  Устраняет ошибку `chtimes …partial: no such file or directory`, которую вызывали
  фоновые службы Synology (индексация/антивирус), удаляя временные файлы.
- **`--max-lock 15m` + `--recover`**: авто-снятие зависших lock-файлов и восстановление
  после прерванных запусков (раньше «prior lock file found» блокировал синхронизацию).
- **Само-восстановление базы bisync**: при потере списков (`cannot find prior … /
  Must run --resync`) враппер сам выполняет `--resync` (раньше нужно было вручную).
- **`export HOME`** в обёртке — единый кэш bisync независимо от способа запуска
  (демон / Планировщик задач / вручную), иначе bisync терял состояние.
- **`--transfers 2 --checkers 4`** — щадящий режим для 1 ГБ ОЗУ DS124.

### Важно (настройка DSM)
- Надёжное периодическое расписание на DSM 7 — через **Планировщик задач** DSM
  (`yandex-disk sync` каждые N минут), т.к. резидентный демон под systemd ненадёжен.
  Подробности — в `README-ARM.md`, раздел «Расписание синхронизации».
- Папку синхронизации стоит **исключить из Индексирования и Антивируса** Synology.

## [0.1.6.1080-9] (ARM) — 2026-05-29

### Fixed
- **Пакет не запускался на DSM 7 (`synopkg start` → код 263 «failed to get unit
  status»).** Причина: в `conf/privilege` была указана `groupname: "sc-yandexdisk"`,
  но такой группы в системе нет — служебный пользователь `sc-yandexdisk` состоит в
  группе `synocommunity`. systemd-юнит пакета не мог разрешить несуществующую группу
  в `Group=` и падал. Возврат `groupname: "synocommunity"` (существующая группа,
  в которой и так состоит пользователь) чинит запуск.

## [0.1.6.1080-8] (ARM) — 2026-05-29

### Added
- **Поддержка ARM64 / aarch64** (Synology DS124, RTD1619B и другие aarch64-модели).
- Нативный движок **rclone v1.74.2** (`linux-arm64`, статически слинкован) с
  встроенным бэкендом Yandex Disk — вместо проприетарного `yandex-disk` CLI,
  который не имеет ARM-сборки.
- Обёртка `yandex-disk` (POSIX sh): `start|stop|status|sync|setup|version|rclone`,
  реализованная поверх `rclone bisync` (двусторонняя синхронизация). Сохраняет
  совместимость с UI пакета и скриптами `yandex-logger` / `yandex-cleaner`
  (в т.ч. строку `Error: daemon not started` для статуса).
- `rclone` добавлен в `conf/resource` (`usr-local-linker`) → доступен как
  `/usr/local/bin/rclone`.
- Документация: `README-ARM.md`, `RELEASE-INFO-ARM.txt`, `build_notes.txt`.
- Скрипты ручной проверки на NAS: `test-on-nas-install.sh`,
  `test-on-nas-functional.sh`.
- `.gitattributes` — фиксирует `eol=lf` для shell-скриптов (защита от
  CRLF при `core.autocrlf=true`).
- Контрольная сумма `YandexDisk-ARM.spk.sha256`.

### Changed
- `INFO`:
  - `displayname`: `Yandex Disk` → `Yandex Disk (ARM)`
  - `version`: `0.1.6.1080-3` → `0.1.6.1080-5` (числовая ревизия — требование DSM; «ARM» вынесено в `displayname`)
  - `conf/privilege` `groupname`: `synocommunity` → `sc-yandexdisk` (самодостаточная группа: на «чистом» NAS группы `synocommunity` нет, из-за чего DSM не создавал служебного пользователя).
  - `arch`: список x86 (apollolake, broadwell, …) → `rtd1619b rtd1296 armada37xx armada38x alpine4k`
  - `description`: дополнено про ARM64 / DS124 / rclone.
  - Поля `package`, `os_min_ver`, `maintainer`, `dsmuidir`, `dsmappname` — без изменений.
- `spk/package/yandex-disk`: бинарник x86_64 заменён обёрткой над rclone
  (оригинал сохранён как `spk/package/yandex-disk.x86_64.backup`, в `.spk` не входит).

### Fixed
- Нормализованы окончания строк **CRLF → LF** во всех shell-скриптах
  (`start-stop-status`, `yandex-logger`, `yandex-cleaner`, `ui/scripts/*.cgi`).
  CRLF (появлявшийся из-за `core.autocrlf=true`) ломал бы `#!/bin/sh` и
  разбор `case/if` при запуске на DSM.
- **Исправлена ошибка установки «Неверный формат файла»** в DSM:
  - `INFO` и `conf/*` нормализованы в LF (CRLF ломал разбор управляющих файлов);
  - версия приведена к числовой ревизии (`-arm`-суффикс отвергался валидатором DSM);
  - `.spk` пересобран с владельцем `root` и без PAX-заголовков (формат GNU tar).
- **Исправлена остановка пакета сразу после запуска** («остановлено вручную»):
  демон `yandex-disk` сделан **резидентным** — `start` всегда запускает фоновый
  процесс, который ждёт настройки (статус «waiting for setup»), а не завершается
  с ошибкой. Теперь DSM показывает «Запущено», а синхронизация стартует
  автоматически в течение ~30 c после настройки OAuth + папки.
- **Исправлено отсутствие пользователя `sc-yandexdisk`**: в DSM 7 пользователь
  создаётся самим DSM из `conf/privilege` (команды `synouser`/`synogroup` в
  скриптах пакета запрещены). Причиной была несуществующая группа `synocommunity`
  — заменена на самодостаточную `sc-yandexdisk`.
- **Пакет сам создаёт `~/.config/yandex-disk/config.cfg`** (каталог + шаблон с
  пустым `dir`) при `start`/`setup`, чтобы не возникала ошибка `E212` при ручном
  создании файла редактором.
- **Парсер `config.cfg` игнорирует инлайн-комментарии и пробелы** (`dir="…"  # …`):
  раньше текст после `#` попадал в значение → rclone падал с `rc=7`. Исправлено в
  обёртке `yandex-disk` и в `yandex-cleaner`; из примера в README убраны инлайн-комментарии.
- **Исключены системные папки Synology из синхронизации** (`#recycle`, `@eaDir`,
  `#snapshot`, `@tmp`, `.DS_Store`, `Thumbs.db`): раньше `rclone` спотыкался на
  `/volume1/<share>/#recycle` с `permission denied` и прерывал bisync.
- **Авто-подбор remote**: если указанного в `config.cfg` имени remote нет в
  `rclone.conf`, а настроен ровно один remote — используется он (терпит, когда
  remote назван иначе, напр. `Yandex` вместо `yandexdisk`).
- **Защита `interval`**: нечисловое значение откатывается к `300` (раньше мусор
  ломал `sleep` в цикле демона).

### Notes
- 32-битные платформы `armada38x` / `alpine4k` присутствуют в `arch` для широты
  установки, но нативный arm64-бинарник на них не запустится — нужна отдельная
  armv7-сборка rclone.
- Функциональная синхронизация с реальным аккаунтом Yandex Disk проверяется на
  NAS (скрипты `test-on-nas-*.sh`); на этапе сборки проверяются структура
  пакета, архитектура бинарника и корректность скриптов.
