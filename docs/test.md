# Тест-план: Yandex Disk (ARM) для Synology DSM

**Тестируемый продукт:** пакет `YandexDisk-ARM-1.1.0.spk` (движок `rclone` v1.74.2, обёртка `yandex-disk`).
**Целевое устройство:** Synology **DS124** (Realtek RTD1619B, aarch64, 1 ГБ RAM).
**ОС:** DiskStation Manager **7.3.2-86009**.
**Автор пакета:** volkovpv (на основе работы VitalityV1nT).
**Составитель тест-плана:** команда «Senior DSM-разработчик + Senior QA».

> Из объёма проверки **исключены** проверка документации и сборки проекта (`build.sh`, CI,
> контрольные суммы, README). Покрываются: **установка, работоспособность, синхронизация, логи,
> UI, интеграция с Планировщиком и жизненный цикл пакета**.

---

## 1. Как пользоваться этим планом

### 1.1. Типы проверок («ящики»)
| Метка | Тип | Что значит для исполнителя |
|---|---|---|
| ⬛ **Ч** | Чёрный ящик | Только GUI DSM и документированные команды. Внутрь файлов не заглядываем. |
| 🟫 **С** | Серый ящик | Документированные команды **плюс** осмотр известных файлов/процессов/состояния. |
| ⬜ **Б** | Белый ящик | Целевая проверка внутренней логики и веток кода (flock, кэш версии, ротация, авто-recover, парсер конфига, коды возврата). |

### 1.2. Правила прогона
- **Тесты выполняются строго по порядку.** Состояние переносится между тестами: настроенный
  remote и базовая точка синхронизации создаются **один раз** (Разделы 3–4) и далее
  переиспользуются — повторно настройку не делаем.
- Каждый тест: **PASS**, если фактический результат совпал с ожидаемым; иначе **FAIL** (зафиксировать вывод).
- Команды выполняются **по SSH** на самом NAS. Многие — от имени пользователя пакета через `sudo -u sc-yandexdisk`;
  `sudo` спросит пароль **вашей учётки администратора DSM** (не пароль `sc-yandexdisk`).
- ⏱ — длительный тест (ожидание расписания/таймера). 🌐 — нужен компьютер с браузером и установленным `rclone`.

### 1.3. Предусловия стенда (выполнить один раз до начала)
1. DS124 на DSM 7.3.2, включён **SSH** (Панель управления → Терминал и SNMP).
2. Учётная запись администратора DSM; на ПК с браузером установлен `rclone` (для OAuth).
3. Действующий аккаунт Яндекс с Яндекс Диском (можно тестовый).
4. Создана общая папка для синхронизации, например `/volume1/yandexdisk`.
5. Файл `YandexDisk-ARM-1.1.0.spk` доступен для загрузки в Центр пакетов.

### 1.4. Переменные окружения для SSH-сессии
Вставьте один раз после входа по SSH — далее шаги используют эти сокращения:
```sh
PKG=/var/packages/YandexDisk
YD=/usr/local/bin/yandex-disk
RCLONE=/usr/local/bin/rclone
U=sc-yandexdisk
CFG=$PKG/home/.config/yandex-disk/config.cfg
RCONF=$PKG/home/.config/rclone/rclone.conf
LOGD=$PKG/var/logs
STATE=$PKG/var/sync.state
```

### 1.5. Справочник путей и процессов (для 🟫 С и ⬜ Б проверок)
| Объект | Путь / признак |
|---|---|
| Обёртка / движок | `$PKG/target/yandex-disk`, `$PKG/target/rclone` (симлинки в `/usr/local/bin/`) |
| Общий код | `$PKG/target/common.sh` |
| Heartbeat / статус-скрипт | `$PKG/scripts/yandex-logger`, `$PKG/scripts/start-stop-status` |
| Скрипты обновления (бэкап данных) | `$PKG/scripts/preupgrade`, `$PKG/scripts/postupgrade` |
| Конфиг приложения | `$CFG` (ключи `dir`, `remote`, `clean_thumbs`) |
| Конфиг remote (токен) | `$RCONF` |
| Состояние синхронизации | `$STATE` (формат `статус\|время\|результат`) |
| История статусов (вкладка «История») | `$LOGD/status_history.log` |
| Реальный лог bisync (вкладка «Журнал синхронизации») | `$LOGD/rclone.log` |
| Метка базовой точки | `$PKG/var/.bisync_resynced` |
| Кэш версии rclone | `$PKG/var/rclone.version` |
| Блокировка одиночного запуска | `$PKG/var/sync.lock` |
| Системный пользователь пакета | `sc-yandexdisk` (группа `synocommunity`) |
| CGI-эндпойнты UI | `/webman/3rdparty/YandexDisk/scripts/{status,log,sync_log,clear_log}.cgi` |

## 5. РАЗДЕЛ 4 — Первая синхронизация и базовая точка

**Предусловие:** Раздел 3 пройден. На локальной папке и на Диске лежит то, что допустимо объединить (первый прогон делает `--resync`).

| # | Тип | Шаги | Ожидаемый результат |
|---|---|---|---|
| **4.1** | ⬜ Б | `sudo -u $U $YD sync; echo "rc=$?"` | Первый прогон выполняет `rclone bisync --resync`. По завершении **rc=0**; создаётся метка `$PKG/var/.bisync_resynced`; `cat $STATE` = `idle\|<дата-время>\|ok`. |
| **4.2** | 🟫 С | `ls -l $LOGD/rclone.log; tail -n 20 $LOGD/rclone.log` | Файл `rclone.log` создан, содержит вывод bisync; строки начинаются с даты и времени (формат `--log-format date,time`). |
| **4.3** | 🟫 С | `sudo -u $U $YD status` | Строка `Последняя синхронизация: <время> (idle/ok)`. |
| **4.4** | ⬜ Б | `cat $PKG/var/rclone.version` | Кэш версии создан (одна строка с версией rclone). |
| **4.5** | ⬜ Б | `echo 'rclone vTEST-CACHE' \| sudo -u $U tee $PKG/var/rclone.version >/dev/null` → `sudo -u $U $YD status \| head -1` → восстановить кэш: `sudo -u $U rm -f $PKG/var/rclone.version; sudo -u $U $YD status >/dev/null` | Первая строка status = `Движок синхронизации: rclone vTEST-CACHE (Яндекс Диск через rclone)`. Это доказывает, что `status` **читает кэш**, а не спавнит 72-МБ бинарник rclone на каждый вызов. После восстановления кэш заполняется реальной версией. |

## 6. РАЗДЕЛ 5 — Функциональная двусторонняя синхронизация

**Предусловие:** Раздел 4 пройден (есть базовая точка). Между шагами расписание Планировщика лучше отключить, чтобы синхронизацией управлять вручную.
**Соглашение:** проверка наличия файла на Диске — `sudo -u $U $RCLONE --config $RCONF lsf yandexdisk: | grep <имя>`.

| # | Тип | Шаги | Ожидаемый результат |
|---|---|---|---|
| **5.1** | 🟫 С | Создать локально: `sudo -u $U sh -c 'echo up > /volume1/yandexdisk/up.txt'` → `sudo -u $U $YD sync` → проверить на Диске. | Файл `up.txt` появился на Яндекс Диске (синхронизация **вверх**). `$STATE` = `idle\|…\|ok`. |
| **5.2** | ⬛ Ч | На Диске (веб-интерфейс Яндекса) создать файл `down.txt` → `sudo -u $U $YD sync` → `ls /volume1/yandexdisk/`. | Файл `down.txt` появился в локальной папке (синхронизация **вниз**). |
| **5.3** | 🟫 С | `sudo -u $U rm /volume1/yandexdisk/up.txt` → `sudo -u $U $YD sync` → проверить на Диске. | `up.txt` удалён и на Диске (удаление синхронизируется в обе стороны). |
| **5.4** | ⬜ Б | Дать файлу `down.txt` отличаться с двух сторон: локально `echo LOCAL > …/down.txt`, на Диске изменить его же на `REMOTE`. Затем один `sudo -u $U $YD sync`. | Срабатывает `--conflict-resolve path1`: **локальная** версия (`LOCAL`) выигрывает и остаётся как `down.txt`. Удалённая версия **не теряется** — сохраняется рядом переименованной копией (напр. `down.txt..path2`/`down.txt.conflict1`). Проверить наличие переименованной копии локально и на Диске. |
| **5.5** | 🟫 С | Создать в папке мусор: `Thumbs.db`, `.DS_Store`, каталог `@eaDir/x.txt`, `#recycle/y.txt` (от `$U`) → `sudo -u $U $YD sync` → `lsf yandexdisk:` рекурсивно. | Ни `Thumbs.db`, ни `.DS_Store`, ни содержимое `@eaDir/`, `#recycle/`, `@tmp/`, `#snapshot/` **не уходят** на Диск (excludes в bisync). |
| **5.6** | ⬜ Б | Включить опцию: дописать в `$CFG` строку `clean_thumbs="1"`. Убедиться, что локально есть `Thumbs.db` и `@eaDir/`. `sudo -u $U $YD sync` → проверить локальную папку. | После sync локальные `Thumbs.db`/`.DS_Store` **удалены** (одноразовая чистка внутри sync). Каталог `@eaDir/` **остаётся нетронутым** (его трогать нельзя — за ним следит индексатор Synology). Вернуть `clean_thumbs="0"` по завершении. |

(Комментарий **без** пробела перед `#` испортит значение — оставлять `#` только через пробел.) |

## 8. РАЗДЕЛ 7 — Подсистема логов (поведение и устойчивость)

Сразу после запуска сентинел-файла нет (до следующего `status`), затем он заполняется актуальной версией — корректный подхват версии после обновления пакета. |
| **7.4** | ⬜ Б | Single-instance heartbeat: при запущенном пакете выполнить `sudo -u $U env YD_PKG_DIR=$PKG $PKG/scripts/yandex-logger; echo "rc=$?"`. | Второй экземпляр немедленно завершается с **rc=1** (страж единственного процесса — `ps … grep '[y]andex-logger'`). Дубля heartbeat нет. |
| **7.5** | ⬜ Б ⏱ | Авто-recover потери базы: остановить расписание; удалить кэш листингов bisync (`rm -f $PKG/home/.cache/rclone/bisync/*`); `sudo -u $U $YD sync`. | В выводе/`rclone.log` фигурирует `Must run --resync` → срабатывает само-восстановление: печатается `[auto-recover] prior listings lost — re-running with --resync`, прогон завершается **rc=0**, `$STATE` = `idle\|…\|ok`. |
