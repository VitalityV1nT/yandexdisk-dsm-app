## 1. Что теперь гарантирует проект (карта гейтов)

Детерминизм обеспечивают **гейты, а не модель** (Г-1 §0): любой результат работы
агента обязан сойтись к зелёному состоянию машинных проверок.

| Команда | Что проверяет | Происхождение |
|---|---|---|
| `bash build.sh` | CRLF-гейт по всем sh-скриптам; `dash -n`; **блокирующий** `shellcheck -S warning`; `checkbashisms` (канон «только POSIX sh»); JSON `spk/conf/privilege`; **гейт дрейфа версий** (`test/check-version-drift.sh`); пиннинг rclone (2×SHA256); ELF-архитектура AArch64 — **жёсткий отказ**; **контракт маркеров** в бинаре rclone (`test/check-rclone-contract.sh`); воспроизводимая сборка `.spk` | W1, W4, W5 |
| `bash test/run-hermetic.sh` | Поведение **без NAS и без живого rclone**: шим `test/fake-rclone` + `YD_*`-оверрайды. **27 сценариев** (T1–T23 + golden G1–G4): машина состояний `run_bisync` (T1–T5, провал первого `--resync` T21), окно счётчиков (T2), single-run guard (T6), ротация и её граница (T7, T19), `is_configured`/`resolve_remote` (T8–T9, T16–T17, T23), парсер `cfg()` (T10), 3/7-полевой `sync.state` (T11–T12), контракт CLI-флагов `_bisync` включая все 6 `--exclude`-масок (T13), кэш `rclone.version` (T14), второй триггер recovery (T15), роутинг подкоманд (T18), `clean_thumbs` (T20), `setup` (T22), golden-снимки (G1–G4, эталоны в `test/golden/`) | W2, W7 |
| `sh test/check-coverage.sh` | Построчное **покрытие** `common.sh`+`yandex-disk` герметичным набором (трассировка bash, без внешних зависимостей). Печатает % и непокрытые строки; порог `YD_COV_MIN` (по умолч. **90 %**/файл). Достигнуто: common 100 %, yandex-disk 96 % | Фаза 1 |
| `bash test/check-reproducible.sh` | Две чистые сборки → один SHA256 (rebuild-twice-and-compare) | W3 |
| `sh test/mutate.sh` | **Мутационный** гейт (аналог Stryker): детерминированные мутации ядра → каждая обязана уронить `run-hermetic.sh`. `mutation score = killed/(total−эквивалентные)`, порог `YD_MUT_MIN` (по умолч. **90**); вет­тированные эквиваленты — `test/mutate.equiv`. **Тяжёлый (~2 мин), on-demand/ночью**, не на каждый push | Фаза 2 |
| CI `.github/workflows/build-spk.yml` | Статика + герметика + **покрытие** + воспроизводимость на **каждый push любой ветки** и PR; на **push в `main`** дополнительно **публикует** Release `v<версия>` с ассетом `YandexDisk-ARM-<версия>.spk` (идемпотентно — только при поднятой версии); actions запинены по commit-SHA | W6 |
| CI `.github/workflows/mutation.yml` | Мутационный гейт **ночью + по кнопке** (`workflow_dispatch`); неблокирующий, push не задерживает | Фаза 2 |
| `CLAUDE.md` + `.github/CODEOWNERS` | Канон агента; защищённый периметр гейтов (`build.sh`, `test/`, workflows — отдельным PR) | W8, W9 |

Уровень зрелости по карте Г-1 §12: **L2 достигнут** (поведение зафиксировано
герметично и в CI), элементы L3 (канон-как-код, периметр гейтов).

**Обязательная цепочка** (Definition of Done любой нетривиальной задачи) — то же,
что гоняет CI на каждый push:

```bash
bash build.sh && bash test/run-hermetic.sh && sh test/check-coverage.sh && bash test/check-reproducible.sh
```

**Мутационный гейт — отдельно** (тяжёлый, ~2 мин; запускать перед сдачей значимой
правки ядра или полагаться на ночной CI):

```bash
sh test/mutate.sh                 # порог YD_MUT_MIN (по умолч. 90)
```

Пороги переопределяются окружением: `YD_COV_MIN=95 sh test/check-coverage.sh`,
`YD_MUT_MIN=100 sh test/mutate.sh`. Красный шаг ⇒ чинится **первопричина в коде**
и цепочка перезапускается с начала. Глушить/ослаблять/обходить проверки запрещено
(Г-1 §0, §3; Г-2 §6).

Вне цепочки остаётся только живой NAS: `test-on-nas-install.sh` и
`test-on-nas-functional.sh` — финальная ручная валидация **перед релизом**, она
дополняет герметичный гейт, но не заменяет его. (Опциональный T14 — герметичный
тест `yandex-logger` — сознательно не внедрён: бесконечный цикл и ps-grep делают
его хрупким в CI, приоритет низкий; см. Г-2 Д-6.)

## 2. Настройка проекта (что требуется)

### 2.1. Инструменты (обязательны — build.sh без них откажет, а не пропустит)

Ubuntu / Debian / WSL2:

```bash
sudo apt update && sudo apt install -y dash shellcheck devscripts python3 unzip curl
```

| Инструмент | Зачем | Примечание |
|---|---|---|
| `dash` | `dash -n` — синтаксис POSIX sh | обычно уже есть |
| `shellcheck` | блокирующий линт (`-S warning`) | есть в ubuntu-latest CI |
| `checkbashisms` (пакет `devscripts`) | принудительный канон «только POSIX sh» | perl-скрипт |
| `python3` | валидация JSON control-файлов | обычно уже есть |
| `tar`, `gzip`, `sha256sum`, `unzip`, `curl`/`wget`, `flock` | сборка, пиннинг, single-run guard в тестах | coreutils/util-linux |

Без `sudo` допустима локальная установка в `~/.local/bin` (так сделано в этой
рабочей сессии: статический бинарь shellcheck v0.11.0 с GitHub releases и
`checkbashisms.pl` из salsa.debian.org) — но канонический путь — `apt`.

### 2.2. Сеть (один раз)

Первая сборка скачивает официальный zip rclone (~24 МБ) с
`downloads.rclone.org` и сверяет **обе** SHA256 (zip и бинарника). Дальше
работает кэш `downloads/`. Без сети сборка возможна, пока валиден
`spk/package/rclone` или кэшированный zip.

### 2.3. Git / переносы строк (урок Д-7)

`.gitattributes` принудительно держит LF для всех скриптов (включая поимённо
`spk/scripts/preupgrade`, `spk/scripts/postupgrade`, `test/fake-rclone`).
При `core.autocrlf=true` ничего настраивать не нужно — но если CRLF-гейт
`build.sh` указал на файл, действие из его подсказки: добавить путь в
`.gitattributes` и перевыкачать файл. **Новый sh-файл без расширения --
сразу перечислить в `.gitattributes` поимённо.**

### 2.4. GitHub (опционально, для полной принудительности W9)

Включить branch protection на `main` с опцией *Require review from Code
Owners* — тогда `.github/CODEOWNERS` физически не даст смержить правку гейтов
без апрува владельца. Без этого CODEOWNERS документирует правило.

### 2.5. Настройки AI-харнесса (Г-1 §6)

- `temperature` 0–0.3; низкий `top_p`; фиксированная (не `latest`) версия модели.
- Модель свободная: Claude-класс для многошаговых рефакторингов, YandexGPT —
  годный генератор для POSIX-sh/русской документации (через OpenAI-совместимый
  эндпоинт Yandex Cloud); **детерминизм даёт гейт, не модель**.
- Креды AI-провайдера — только из окружения, никогда в репозиторий.
- Контекст агента фиксирован: `CLAUDE.md` подхватывается автоматически; в
  промпте при необходимости указывать конкретные файлы, а не «найди сам».

## 3. Промпты процесса

Ниже — готовые шаблоны. Общий принцип (Г-1 §8): **привязывай к гейту, называй
контракт, очерчивай периметр, требуй тест на новое поведение.**

### 3.0. Базовый каркас (вставляется в каждую задачу)

```text
Задача: <что сделать и зачем, 1–3 предложения>.

Канон: следуй CLAUDE.md (контракты лога/sync.state/UI, security-инварианты,
периметр: не трогать test_package/, *.backup, downloads/, готовые *.spk).

Гейт (Definition of Done): доведи до зелёного
    bash build.sh && bash test/run-hermetic.sh && bash test/check-reproducible.sh
Если шаг падает — чини первопричину в коде и перезапускай цепочку с начала.
Запрещено глушить/ослаблять проверки и править build.sh, test/,
.github/workflows/ в этой задаче (это отдельный PR с моего одобрения).

Периметр правок: <список файлов/каталогов, например: только spk/package/yandex-disk и spk/package/common.sh>.
```

### 3.1. Рефакторинг существующей фичи (characterization-first, Г-1 §11.4)

Два промпта, строго по очереди (страховочная сеть — до правок кода):

**Шаг А — зафиксировать текущее поведение** (это правка `test/` ⇒ отдельный PR):

```text
Задача: добавь в test/run-hermetic.sh герметичные сценарии (и при
необходимости golden-эталоны в test/golden/), фиксирующие ТЕКУЩЕЕ поведение
<фичи X: какие входы, какие наблюдаемые выходы>. Код пакета (spk/) НЕ менять.

Mutation-sanity нового теста: временно внеси в код минимальную поломку
поведения X, покажи, что новый сценарий падает, откати поломку.
Помни: T3 в run-hermetic.sh должен идти до сценариев, пишущих триггер
recovery в лог (см. комментарий в шапке файла).

Гейт: bash build.sh && bash test/run-hermetic.sh && bash test/check-reproducible.sh.
```

**Шаг Б — сам рефакторинг под зелёным:**

```text
Задача: отрефактори <X>: <цель — упростить/вынести в common.sh/убрать дубли>.
Поведение менять НЕЛЬЗЯ: все сценарии test/run-hermetic.sh и golden-эталоны
обязаны пройти БЕЗ изменения эталонов. Если рефакторинг требует изменить
эталон — остановись и спроси: это смена контракта, а не рефакторинг.
<базовый каркас 3.0>
```

### 3.2. Новая фича (контракт раньше реализации, DoD = новый гейт, Г-1 §11.5)

```text
Задача: добавь <фичу Y>.

Сначала контракт, потом код:
1) Зафиксируй контракт: <новая подкоманда yandex-disk / новое поле sync.state /
   новый ключ config.cfg / новый CGI+вкладка UI — точный формат>.
   Если контракт расширяет sync.state или меняет вывод status — старый формат
   обязан остаться читаемым (обратная совместимость, как 3-полевой state).
2) Реализуй по канону: общие величины — сначала в common.sh; только POSIX sh;
   новый скрипт → в POSIX_SH в build.sh (это разрешённая правка build.sh,
   назови её в отчёте отдельно) и, если без расширения, — в .gitattributes.
3) Definition of Done фичи = новый герметичный сценарий Tnn в
   test/run-hermetic.sh (+ golden, если меняется человекочитаемый вывод):
   без него фича не принята. Новая подкоманда обязана попасть в usage и README.
4) Mutation-sanity: покажи, что новый сценарий падает при сломанной фиче.

<базовый каркас 3.0, периметр: spk/... + test/run-hermetic.sh>
```

### 3.3. Правка самих гейтов (защищённый периметр, W9)

Только отдельной задачей/PR, без смешивания с кодом пакета:

```text
Задача: <правка build.sh / test/ / workflows: что и зачем>.
Это PR только по гейтам: код пакета (spk/) не трогать.
После правки прогони mutation-sanity по таблице Г-2 §5 (6 диверсий:
маркер счётчика, поле sync.state, bashism, mtime, exclude-маска, x86-бинарь):
каждая диверсия должна сделать свой гейт красным; гейт, не упавший на своей
диверсии, чини (гейт, а не таблицу). Воспроизводимость: SHA256 .spk не должен
измениться, если правка не меняет содержимое пакета намеренно.
```

### 3.4. Бамп версии rclone

```text
Задача: подними rclone до <vX.Y.Z>.
Обязательный цикл (Г-2 §6 п.6), не пропускай шаги:
1) Новые URL + ОБЕ SHA256 (zip и бинарника) в build.sh — суммы возьми с
   официального downloads.rclone.org (SHA256SUMS), не вычисляй по скачанному.
2) bash build.sh: контракт-гейт test/check-rclone-contract.sh обязан остаться
   зелёным — если какой-то маркер пропал из бинаря, СТОП: это смена контракта
   счётчиков/recovery, нужно моё решение.
3) Версия движка в RELEASE-INFO-ARM.txt и README.md (таблица) — гейт
   check-version-drift.sh подскажет, где забыл.
4) Обнови версию шима test/fake-rclone (строка version) — golden G1/G2 при
   этом НЕ должны измениться (они снимаются с шима; если изменились — обнови
   эталон осознанно в том же коммите).
5) Полная цепочка + ручная валидация на NAS перед релизом.
```

### 3.5. Релиз

```text
Задача: подготовь релиз <X.Y.Z> (<мажор/минор/патч> — обоснуй по правилам
CHANGELOG-ARM.md «Версионирование»).
1) Версия синхронно: spk/INFO + новая запись в CHANGELOG-ARM.md +
   RELEASE-INFO-ARM.txt (Version, Build date, имя .spk в 3 местах).
2) bash build.sh → впиши фактические SHA-256 и размер .spk в RELEASE-INFO.
3) Полная цепочка зелёная; затем ручная test-on-nas-functional.sh на NAS.
4) Открой PR с этим bump; после моего одобрения и мержа в main CI сам соберёт
   YandexDisk-ARM-<X.Y.Z>.spk, создаст тег v<X.Y.Z> и опубликует Release.
   Релиз привязан к bump версии: пока версию в spk/INFO не подняли, мерж в main
   новый Release не создаёт (идемпотентность по существующему v<версия>).
```

### 3.6. Двухагентный режим (proposer / checker, Г-1 §11.6 — опционально)

Промпт второму, независимому агенту (или второй сессии) после того, как первый
сдал задачу:

```text
Ты — независимый ревьюер. Проверь дифф <ветка/PR> против чек-листа Г-1 §7:
POSIX-sh и POSIX_SH-список; общие величины из common.sh, не скопированы;
контракты целы (4 лог-маркера, 7-полевой sync.state + старый 3-полевой,
ключи UI/CGI, remote yandexdisk); нет резидентного демона; секреты/ПДн не
появились; exclude-список цел; гейты и эталоны не ослаблены и не «подогнаны»
(diff по build.sh, test/, test/golden/ — объясни каждую правку там).
Вердикт верни структурно: {файлы, нарушения[], вердикт: ok|reject, причина}.
Код не правь.
```

### 3.7. Когда агент обязан остановиться и спросить (из CLAUDE.md)

Ослабление security-инварианта; смена версии rclone; возврат резидентного
демона; изменение любого контракта (лог-маркеры, sync.state, ключи UI/CGI, имя
remote); флаги воспроизводимости build.sh; изменение, проверяемое только на
живом NAS. Правильная реакция на просьбу «выключи проверку, чтобы прошло» —
отказ + первопричина + риск (Г-1 §2.6).

## 4. Регулярные процедуры

### 4.1. Mutation-sanity (раз в N задач и при каждой правке гейтов)

Таблица Г-2 §5 — внести диверсию, увидеть красный, откатить:

| # | Диверсия | Обязан упасть | Проверено 2026-06-13 |
|---|---|---|---|
| 1 | `Queue copy to Path2` → `…PathX` в `count_run_transfers` | `run-hermetic` T1 (f4=0) | ✅ |
| 2 | минус поле в `printf` `write_sync_state` | `run-hermetic` T1/T12/golden | ✅ |
| 3 | `[[ -n "$LOCAL" ]]` в `yandex-disk` | `build.sh` (shellcheck SC3010; `dash -n` это синтаксически пропускает — потому линтеры и обязательны) | ✅ |
| 4 | `--mtime` → текущее время в `build.sh` | `check-reproducible` | ✅ |
| 5 | удалить `--exclude "@eaDir/**"` | `run-hermetic` T13 | ✅ |
| 6 | x86-бинарь вместо rclone **+ подогнанный `RCLONE_BIN_SHA256`** (иначе fetch сам восстановит правильный бинарь — это тоже защита) | ELF-гейт `build.sh`, exit 1 | ✅ |

### 4.2. Re-run convergence (диагностика недоопределённости, Г-1 §11.6)

Изредка: одна задача, два независимых прогона агента в двух worktree. Оба
зелёные, но семантически разные ⇒ спецификация недоопределена ⇒ добавить
тест/golden, закрывающий разошедшуюся степень свободы (ужесточить гейт, а не
«уговаривать» модель).

### 4.3. Обновление golden-эталонов

Эталон меняется только **осознанно, в том же коммите, с объяснением** в
сообщении коммита/PR (сообщение гейта G1–G4 об этом напоминает). Перегенерация:
выполнить соответствующую команду из `run-hermetic.sh` вручную или временно
скопировать `$WORK/actual` — и обязательно объяснить дифф.
